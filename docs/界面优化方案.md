# 口袋服务器 PocketServer · 界面优化方案

> 范围：手机端（10 屏）、Android TV 端（4 屏）、电脑端内嵌网页（`WebUi.kt`）
> 性质：**分析与计划**。本文档不包含任何代码改动，所有结论附 `文件:行号` 证据。
> 审计基线：`WebUi.kt`(9/30 13:53)、`ConsoleScreen.kt`(9/29 16:12)、`TvConsoleScreen.kt`(9/30 10:14) 等当前工作区版本。

---

## 摘要

**结论：这个项目的功能完成度远高于界面完成度。**

工程侧的证据很硬 —— 11 个测试类 / 155 个用例、内嵌网页 52 条 DOM 断言 + 62 条 Playwright 断言、`需求追溯矩阵.md` 逐条对码、README 把每处取舍的原因都写下来了。这些说明"想清楚了才写"。

但界面层暴露出 **3 个根因级问题**，它们派生出了大量症状：

| # | 根因 | 派生症状 |
|---|---|---|
| R1 | **手机端没有"页面骨架"这个概念** —— 全项目仅一处 `Scaffold` 且未配 `topBar` | 标题随滚动消失、4 个二级页 3 个没有返回键、tab 名与页面标题不一致 |
| R2 | **控制台首屏的信息层级是反的** —— 最该做的事最不显眼 | 主操作是 32dp 的 Switch、次要的"开始测速"是全宽大按钮、服务未开时首屏几乎空白 |
| R3 | **设计 token 体系缺位** —— 颜色有 `colorScheme`，但间距/圆角/（网页）所有样式都是散落字面量 | 深色模式半成品、多处硬编码色绕过主题、网页 CSS 两层叠加且有色值双套 |

> **两点必要的限定**（采纳评审意见后补充）：
> 1. 这 3 个根因只解释**各自对应**的那批症状，不等于"所有视觉问题都源于缺骨架或缺 token"。第 7 节那批缺陷（倒计时不自更新、toast 遮挡、日志清空无确认…）与它们无关，必须单独修。
> 2. 引入统一组件与设计变量能**减少重复与漂移**，但不保证界面自然就变好。每一屏仍要用**当前版本**的截图与实际使用流程逐一验证 —— 这项验证已写进第 0 批与第五节。

另有 **2 个独立的重要缺口**：

- **电视端焦点管理基本空白**（`focusRequester` / `bringIntoView` / `traversalIndex` / `BackHandler` 全项目 0 处）。这是十尺 UI 的命门。
- **电视端退出界面后，新设备接入请求无人承接**，只能等 60 秒自动拒绝（`TvApp.kt:114-121` + `:282`）。而电视端的定位是 7×24 常驻。**这是我认为全项目最该优先修的一条。**

## 一、现状诊断

### 0. 先纠正一个前提：现有截图已过期

`docs/webui/` 下的 4 张图是 **9/23 17:18** 生成的，而 `WebUi.kt` 改到 **9/30 13:53**。
中间加入了 `/* Refined PocketServer web UI */` 整层样式（`WebUi.kt:2366-2579`）、四种视图切换（小图/中图/大图/侧边栏）、文件夹收藏、批量选择条。

另外 README 口径与代码不符：README:170 写"电视端 5 屏"，实际 `TvRoute` 只有 4 条路由（`TvApp.kt:41-46`），第 5 个文件是外壳。

### 1. 手机端：缺"页面骨架"，导致一串不一致（R1）

**证据**：全项目**只有一处 `Scaffold`**（`PhoneApp.kt:102`），且**没有配 `topBar`**（只有 `bottomBar:103-131` 与 `snackbarHost:132`）。

于是每屏都自己解决"标题放哪"：

- 标题写在**可滚动内容**里 —— `ConsoleScreen.kt:123-130`（标题在 `verticalScroll` 的 `Column` 内）、`SettingsScreen.kt:108-118`、`BackgroundAndCleanup.kt:204-209`。**滚动即消失，无吸顶**。
- 返回键各行其是：

| 二级页 | 返回键 | 证据 |
|---|---|---|
| 存储与清理 `cleanup` | **有** | `BackgroundAndCleanup.kt:211-214`（`IconButton` + `popBackStack`） |
| 访问日志 `logs` | **无** | `LogsScreen.kt:79-81`（右侧只有"清空"） |
| 已连接设备 `connected` | **无** | `ConnectedScreen.kt:75-87` |
| 二维码 `qr` | **无** | `QrDisplayScreen.kt:102-112` |

根因不止是"忘了画"：`PhoneApp.kt:158-160` 注册这三条路由时**根本没注入返回回调**，即便想画也无从实现。只有 `cleanup` 在 `PhoneApp.kt:163` 传了 `onBack`。

- tab 名与页面标题口径不一：底栏「文件 / 附近 / 传输」（`PhoneApp.kt:56-62`）对应页面标题「本机文件 / 附近设备 / 传输任务」（`FilesScreen.kt:110`、`NearbyScreen.kt:114`、`TransfersScreen.kt:81`）。

> **判断**：这是**修一处可连带解决 4~5 条**的问题。引入统一 `ScreenScaffold`（标题 + 可选返回 + 动作槽）是性价比最高的结构改动。

### 2. 手机端控制台：信息层级是反的（R2）

**证据链（全部在 `ConsoleScreen.kt`）**：

| 现象 | 证据 |
|---|---|
| 服务未开启时，地址 / 配对码 / 运行情况 / 测速**全部不渲染** | `:139` `if (state.running)` 包裹 `:140-183` |
| 启停服务是**一个 32dp 的 Switch，没有文字** | `:288` `Switch(checked = running, onCheckedChange = { onToggle() })` |
| 次要功能"开始测速"反而是**全宽填充大按钮** | `:519-527` |
| 服务运行时，32sp 配对码 + 22sp URL + 4 个 22sp 粗体指标**同时争视觉焦点** | `:402-409`、`:363-368`、`:443-445`、`:459` |
| "主机名 URL" 与 "IP 备用地址" 的关系**界面完全不解释** | `:364`（`primaryUrl` 可能是域名也可能是 IP，见 `Models.kt:89-93`） vs `:388`（"备用地址"） |
| 「二维码」入口用**扫码**图标表示**展示**二维码 | `:380` `Icons.Default.QrCodeScanner` —— 语义相反 |

对用户三个核心问题的实际回答质量：

1. **服务开没开？** 好。`ServiceHeaderCard` 首屏第一块，运行态整卡变绿 + `CheckCircle`（`:228`、`:238`、`:246`）。
2. **电脑该访问哪个地址？** 中。地址醒目（22sp Bold），但**未开启时完全看不到**。
3. **下一步做什么？** 弱。只有一句 `StatusDot` 提示（`:264-267` "开启后才能被电脑访问"），没有任何"点这里启动"的显式文案。

### 3. 深色模式是半成品（R3）

| 问题 | 证据 |
|---|---|
| **手机深色直接复用电视的深色盘** | `Theme.kt:104-106`：`if (isSystemInDarkTheme()) TvDarkScheme else PhoneLightScheme`。而 `TvDarkScheme` 的注释明确写着是为 2~3 米客厅防眩光调的（`Theme.kt:38-44`），其 `primary #6FA8FF` / `secondary #4FD1B5` 在大屏远距可读，**在手机上偏荧光** |
| **`tertiary` 未定义** | `TransfersScreen.kt:298` 用 `colorScheme.tertiary` 做"已暂停"状态色，两套 scheme 都没定义 → **回落 M3 默认紫**，与整体配色游离 |
| **3 处硬编码色不随主题变化** | `ConsoleScreen.kt:228` 绿卡 `#25A76B`、`:330` 渐变环 `#35E6D0`/`#8C7BFF`、`FilesScreen.kt:365` 橙图标 `#F4AA22` |
| **对比度不达标** | 绿卡 `#25A76B` 上的白字对比约 **3.1:1**，低于正文 AA 的 4.5:1（`:246` 16sp、`:253-267` 14sp、`:339-344` 11sp） |
| **Banner 的 Warn/Success 是浅色硬编码** | `Common.kt:219` `#FFF3E0`/`#8A5300`、`:221` `#E7F7EE`/`#116039`。在电视深色界面上是**两块刺眼的浅色块**。对照 `Error` 分支用了 `colorScheme.error.copy(alpha)`（`:220`），是自适应的 —— **同一组件三种自适应策略** |
| **系统栏不跟随** | `themes.xml` 手机主题固定 `android:Theme.Material.Light.NoActionBar` + `windowLightStatusBar=true`；`MainActivity.kt:55-57` 只按 `isTv` 选主题，**不看系统深色** → 系统深色时内容变深、状态栏仍是浅色 + 深色图标，启动瞬间还闪一下白 |

### 4. 电视端：焦点管理空白（十尺 UI 的命门）

**全 `ui/` 目录 grep 结果：`focusRequester` / `FocusRequester` / `bringIntoView` / `focusProperties` / `traversalIndex` / `onKeyEvent` / `BackHandler` —— 0 匹配。**

| 现象 | 证据 | 后果 |
|---|---|---|
| **进入电视端无初始焦点落点** | `TvApp.kt:89-112` 直接 `Row { TvNavRail(); Box { when(route) } }`，无 `requestFocus()` | 首次按键前屏幕上**没有任何焦点框**，用户"按了没反应" |
| **切页焦点不复位** | `TvApp.kt:74, 105-110` | 选中导航项后焦点停在左栏，要**再按一次**才能进内容区 |
| **弹窗默认焦点与注释承诺不符** | 注释称"默认焦点落在「允许」上"（`TvApp.kt:239-244`），实现只是普通 `TextButton`（`:296-304`），无 `focusRequester` | Material3 不保证落在 confirmButton，**可能落到"拒绝"** |
| **`.clickable()` 与 `.focusable()` 叠加** | `TvApp.kt:195-196`、`TvComponents.kt:68-69, 122-123`、`Common.kt:194-195`（4 处） | 形成**两个 focus target**，可能"同一行按两次键"；`onFocusChanged` 还放在 `focusable()` 之后（顺序也不符官方建议） |
| **列表/网格无主动滚屏** | `TvFilesScreen.kt:143-193`、`TvRecentScreen.kt:97-112` 均未传 `LazyListState`，无 `bringIntoViewRequester` | 3 列网格（`TvRecentScreen.kt:98`）边缘行焦点可能跑出可视区 |
| **焦点态实现被手写 4 遍** | `TvApp.kt:170-230`、`TvComponents.kt:43-86`、`:97-157`、`Common.kt:179-206` | `TvTokens.FOCUS_BORDER_DP`（`Theme.kt:119`）**只被 1 处使用**，另 3 处硬编码 `3.dp`（`TvApp.kt:186`、`TvComponents.kt:63, 110`） |
| **无 `BackHandler`** | 全项目 0 处 | 顶层单次返回**直接退出**，无"再按一次"确认 |
| **服务停止时仍展示看似有效的二维码/配对码** | `TvConsoleScreen.kt:131-198` 无 `running` 判断。对照手机端 `QrDisplayScreen.kt:114-119` **有** Banner 提示 | 用户拿无效码去扫，失败后无从判断原因 |

**最关键的一条（我列它为全项目最高优先级）：**

> **E1 — 退出电视端界面后，接入确认闸门失去承载界面。**
> `TvAccessConfirmDialog` 挂在外壳层 `TvApp`（`TvApp.kt:114-121`）。用户一旦退出电视端界面，新的接入请求**没有任何界面可承接**，只能等 60 秒自动拒绝（`TvApp.kt:282`）。
> 而电视端的定位是"进入即自动启动、7×24 常驻"。这等于**常驻服务在最需要它的场景下失联**，且对方那侧只是"连不上"。

### 5. 网页端：能力强、骨架弱

**先把事实说清楚：网页端的功能其实相当全。**
从代码看（`WebUi.kt`），它已经具备：四种视图（小图/中图/大图/侧边栏 `:212-217, 2530-2532`）、排序（名称/大小/修改时间 `:240-244`）、多选批量下载 ZIP 与批量删除（`:226-233, 977-1006`）、文件夹收藏（`:221-224`）、window 级拖拽（`:1062-1112`）、断点续传、任务暂停/继续/取消、设备切换菜单（`:185-197`）。

**问题集中在"骨架"与"打磨"：**

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| W1 | **CSS 两层叠加，后层重写同名选择器** | 基础层 `:2256-2364` + `/* Refined */` 层 `:2366-2579` | 存在死 CSS；同色值两套（主按钮 `#246bfd` 纯色 `:2286` vs 渐变 `:2393`；`.act` `#1f6feb` `:2301` vs `#41648f` `:2414`） |
| W2 | **零 CSS 变量** | 全文件无 `:root` / `var(--)` | 圆角出现 6/7/8/9/10/11/12/14/16/17/20/99/999 **十三种**；色值散落十余处 |
| W3 | **无深色模式** | 无 `prefers-color-scheme` / `color-scheme`（0 处） | 夜间刺眼 |
| W4 | **键盘路径不完整**（初版写作"键盘几乎不可用 / 需补 tabindex"，**已修正**） | 全文件**只有**两条 `.code-input:focus` 规则（`:2358, 2441`），且**没有任何 `outline:none`** → 原生 `button`/`a`/`select` 的默认焦点环**是保留的**，也不需要给它们加 `tabindex`。真正缺的是两件事：① **拖拽上传（`#drop`）没有任何键盘替代入口**（上传按钮存在，但整页拖拽这一主要路径对键盘用户不存在）；② 文件列表行由 JS 生成 `div`（无 `role`、无方向键导航），5000 个文件靠 Tab 逐个走不可行 | 键盘与读屏用户无法完成"上传"和"在大目录里定位"；鼠标用户不受影响。**这是可达性缺口，不是"焦点不可见"** |
| W5 | **无加载态** | `load()` 期间列表区无占位（`:701-723`） | 弱网下"空目录"与"加载中"分不清 |
| W6 | **无搜索/筛选** | 前端无输入框；后端 `handleList` 只接受 `path`（`HttpFileServer.kt:816-825`） | 大目录无法定位 |
| W7 | **无分页/虚拟滚动** | 后端一次返回全部条目（`HttpFileServer.kt:838-875`），前端全量建 DOM（`:793-900`）。`MAX_ROWS=300` **只作用于传输任务行**（`:304, 1622-1627`） | 上万文件目录卡顿 |
| W8 | **不显示修改时间** | API 已下发 `mtime`（`HttpFileServer.kt:859`）且支持按 mtime 排序，行内只渲染 size（`:864`） | **按时间排序却看不到时间** |
| W9 | **两条进度条语义冲突** | 总体条 `#tbar` 只被写宽度、**永不加 done/fail 类**（`:1277`）→ 恒蓝；行内条却红绿黄三态（`:1632-1637, 2335-2338`） | 概览看不出批次成功还是失败 |
| W10 | **Toast 遮挡底部传输面板** | `.toast{position:fixed;bottom:28px}`（`:2349`）+ `#tasks` 在文档流末（`:268-278`） | 滚到底时提示盖住任务行（9/23 截图里已能看到重叠） |
| W11 | **首屏竖向留白** | `.list-wrap{min-height:clamp(260px,44vh,480px)}`（`:2402`） | 文件少时下方大片空白（截图可见） |
| W12 | **头部缺状态层级** | 无只读会话徽标；无剩余空间 —— API 的 `free`（`HttpFileServer.kt:872`）与 `fullStorage`（`:811`）**前端从未使用**（grep `d.free` 0 处） | 用户无法一眼确认权限与空间 |
| W13 | **断开无二次确认** | `:2185-2187` 直接 `POST /api/logout` + `location.href='/pair'` | 断开后要重新配对码 |
| W14 | **拖拽/重命名/新建依赖原生对话框** | `window.prompt`/`confirm`（`:1033, 1041, 1052, 995`） | 风格不统一、移动端体验差 |
| W15 | **`errorPage` 是死代码** | 定义在 `:2603-2611`，**无任何调用方**；未匹配路由返回裸 `text/plain`（`HttpCore.kt:546-552`） | 与"零依赖也要体面"的定位不符 |
| W16 | **读目录失败时列表区全空且无说明** | `:711-717` 清空 `#list`、隐藏 `#empty`，只弹 5 秒 toast | 失败后用户盯着空白页 |

### 7. 一组"真错"（不是审美问题，是缺陷）

| # | 缺陷 | 证据 |

| B6 | **设置页「维护」卡里"访问日志"入口重复两次** | `SettingsScreen.kt:398-403`（`ClickableRow`）与 `:434-441`（`OutlinedButton`），目标相同 |

| B8 | **`TvRecentScreen` 无加载态** → 数据未就绪先闪一次空态 | `TvRecentScreen.kt:89-95` |

## 二、改造方案（四批）

### 第 0 批 · 证据刷新（约 0.5 天）

### 第 2 批 · 视觉地基（约 2~3 天，收益全局）

**这批是"调整空间"最大的地方** —— 它不改变功能，但决定了后面所有改动的观感质量。

**2.1 建立 design token 体系**

- **Compose 侧**：新增 `Spacing` 与 `Radius` token 对象。现状是间距出现 2/4/6/8/10/12/14/20/24 dp 全部值（无 token），圆角出现 12/14/18/20/22，其中 **`SectionCard` 硬编码 20dp**（`Common.kt:50`）、`Banner` 12dp（`:226`）、二维码盒 18dp（`QrDisplayScreen.kt:125`），而主题提供的是 6/10/14/18/22（`Theme.kt:73-79`）—— **20dp 不属于任何 token，等于绕过了 `MaterialTheme.shapes`**。
- **网页侧**：`:root` 定义 `--ps-color-*` / `--ps-radius-*` / `--ps-space-*` / `--ps-font-*`，**把基础层与 Refined 层合并成一层**，删掉死 CSS（W1+W2）。同时删掉无对应 DOM 的规则（`.preview`/`.preview-panel`/`body.preview-open`/`.connected`/`.toolbar .secondary`）。

**2.2 深色模式补齐**

- **拆出手机端独立深色盘**，不再复用 `TvDarkScheme`。手机深色的目标是"夜间不刺眼"，应比电视盘**低饱和、去荧光**；同时把 `tertiary` 定义出来，消掉 `TransfersScreen.kt:298` 的 M3 默认紫。
- 3 处硬编码色收进主题（绿卡、橙图标、渐变环）。建议新增语义色 `success` / `warning`，而不是复用 `secondaryContainer`（避免语义混淆）。
- **`Banner` 的 Warn/Success 改成自适应**（与 `Error` 一样走 alpha 叠色）。否则电视深色界面上永远有两块浅色块。
- **`themes.xml` + `MainActivity` 联动系统深色**，消掉启动闪白与系统栏割裂。这一条看似小，但它决定了深色模式"像不像一个做完的功能"。
- 顺带修 `ConsoleScreen.kt:228` 绿卡的白字对比度（3.1:1 → 目标 ≥ 4.5:1）。

### 第 3 批 · 结构改造（约 1~1.5 周，解决根因）

**3.1 手机端：引入统一 `ScreenScaffold`**（解 R1）

一个 `Scaffold(topBar = TopAppBar(标题 + 可选返回 + actions))`，把 10 屏的标题、返回、动作全收进去。
连带解决：标题滚动消失、二级页返回不一致、tab 名与页面标题不一致。
收口点在 `PhoneApp.kt:102-164` —— 需要给 `logs` / `connected` / `qr` 注入 `onBack`（现在 `:158-160` 没传）。

**3.2 手机端控制台：重排信息层级**（解 R2，这是我最想改的一屏）

**未运行态**（现状：几乎空白）：
- 一句目标："让电脑访问这部手机"
- **全宽主按钮「启动服务」**（取代 32dp 的 Switch）
- 三步预告：连同一个 Wi-Fi → 启动服务 → 电脑输地址
- 测速、运行情况**收起**

**运行态**：
- 大 URL + 「复制 / 二维码」在首屏最上
- 配对码紧随其后（仍是视觉最重）
- 运行指标从 4 个 22sp 粗体数字压成**一行紧凑状态条**，可点开详情
- 测速降级为次要文字按钮

另外两处必须明确的：
- **解释"主机名 vs IP"的关系**（`primaryUrl` 可能是 `pocketserver.local` 也可能是 IP，界面目前不解释主次）
- 「二维码」入口换正确图标

**3.3 电视端：把焦点系统真正落地**（这是十尺 UI 的命门）

1. 抽一个统一的 `TvFocusable` 容器，替换 4 份手写焦点态，统一走 `TvTokens`
2. 加 `FocusRequester`：进入页面落到内容首项；切页复位
3. 接入确认弹窗补默认焦点到「允许」（兑现 `TvApp.kt:239-244` 的注释承诺）
4. 去掉冗余的 `.focusable()`（4 处），修正 `onFocusChanged` 位置
5. 列表/网格挂 `LazyListState` + `bringIntoViewRequester`
6. 加 `BackHandler` 做"再按一次退出"
7. `route` 改 `rememberSaveable`；`TvRecentScreen` 补加载态；`TvFocusableCard`/`TvNavItem` 补 `minHeight`

**3.4 电视端：修 E1（我列的最高优先级）**

电视端定位是 7×24 常驻，但退出界面后接入确认无人承接。方案三选一：

| 方案 | 做法 | 评价 |
|---|---|---|
| a) 退出前拦截 | 退出时若有待处理接入请求或服务在跑，弹确认并说明"退出后将无法确认新设备接入" | 改动最小，但只是"告知" |
| b) **通知承接** | 退出后落到前台服务的常驻通知，通知带「允许 / 拒绝」动作 | **推荐**。这是 Android 上"常驻服务器"类应用的标准形态，也顺带解决"退出后无法确认接入" |
| c) 闸门策略降级 | 退出后自动切到免确认或延时 | 有安全代价，不建议 |

**建议 a + b 组合**：先拦截确认，再让通知承接。

> **成本复核（采纳评审意见后实测代码，结论：低于"高"，但确实高于初版的"中等"）**
>
> 评审认为"通知承接"涉及后台服务、通知权限与安全流程，成本不止中等。**方向对，但架构侧的门槛已经被跨过了**：
>
> `AccessGate` 是一个**纯内存、与界面无关**的类（`AccessGate.kt:32-114`），它已经暴露了
> `requests: StateFlow<List<AccessRequest>>`（`:44-46`）、`decide(id, allow)`（`:86-90`）、
> `hasPending()`（`:98`）、`rejectAll()`（`:101-109`），甚至有一个**专门为电视遥控器写好的
> `decideOldest(allow)`（`:92-96`）**。并且它在 `AppModule.kt:79-81` 是 `@Singleton`
> （`SingletonComponent`），HTTP 服务与任何界面**共享同一实例**；`AppModule.kt:126-130`
> 也已经提供了专门承载"比任何界面活得久"的任务的 `@ApplicationScope`。
>
> 也就是说：**状态机、订阅入口、决议 API、后台作用域全部现成**。通知方案不需要改动闸门、
> HTTP 服务或确认流程本身。真正的工作量是样板活：新建通知渠道、`POST_NOTIFICATIONS`
> 运行时权限（API 33+）、两个 `PendingIntent` 接到 `gate.decide`、退出/停服时撤销通知。
>
> **成本评级：中 → 中高**（初版写"中等"偏低，评审这一条成立）。
> 主要风险不在写代码，而在**验证**：需要真机 + 通知权限流程 + "退出界面后由另一台设备发起接入"的完整场景回归。
>
> 若想先拿到收益再决定形态：**最便宜的中间步骤是 a** —— `hasPending()` 现成，退出前拦截大约十行。

**3.5 网页端：骨架重构**

| 项 | 做法 |
|---|---|
| CSS | 合并单层 + `:root` 变量（同 2.1），顺带清死代码 |
| 深色 | 补 `prefers-color-scheme` |
| 键盘 | **不补 `tabindex`**（原生控件本就可聚焦，补了反而打乱顺序）。改为：为拖拽上传提供**按钮/快捷键替代入口**、给文件列表加**方向键导航模型**（`role=listbox` 或 roving tabindex）、补自定义 `:focus-visible` 让焦点环在彩色按钮上足够清晰（W4） |
| 加载 | 补骨架屏 / 加载态 + **常驻断线提示**（现在是 5 秒 toast，断了就没参照） |
| 读取失败 | 列表区给出明确失败说明与「重试」按钮，不要只弹 toast（W16） |
| 状态层级 | 头部补**只读会话徽标** + **剩余空间**（API 已有 `free`，只是没用，W12） |
| 进度条 | 总体条与行内条统一三态语义（W9） |
| 布局 | `list-wrap` 的 `min-height` 降下来消掉留白（W11）；toast 挪位避开底部传输面板（W10） |
| 列表 | 行内补**修改时间**（W8） |
| 搜索 | 前端过滤当前目录**立刻可做**；全盘搜索需后端加 query 参数 |
| 性能 | **不要用"截断到 N 条"当解法** —— 用户会以为文件丢了。首选**虚拟列表**（保留全量元数据，只渲染可见窗口）+ **明确显示"共 N 项，当前显示第 1–M 项"**；截断兜底仅在虚拟列表暂不可行时使用，且必须同时显示总数。理由：客户端排序/搜索本来就需要全量元数据，做**服务端分页会把排序也一并搬到服务端**，对一个局域网文件服务器是净负担（W7） |
| 对话框 | `prompt`/`confirm` 换成自绘对话框，或至少统一风格（W14） |
| 404 | 让 `errorPage` 真正生效，替换裸 `text/plain`（W15） |

> **评审提出、但本次审计尚未核实的网页项**（列在这里以免被当成已确认结论）：
> - **当前路径保留**：刷新或切设备后，`cwd`（`WebUi.kt:296`）从根目录重新开始，用户需重新点回深层目录。是否值得做"会话内记忆路径"需先确认实际使用频率。
> - **设备自动发现**：头部「切换设备 · N 在线」菜单目前依赖手工填地址（`:190-194`）。是否有自动发现路径、体验如何，未在本次范围内核实。
> - **批量操作**：**代码里已有多选 + 批量下载 ZIP + 批量删除**（`:226-233, 977-1006`），所以它属于"验证与打磨"，不是待开发功能 —— 注意别被 `docs/webui/` 里 9/23 的旧截图误导成"功能缺失"。
> - 另外评审强调的"加载失败要常驻说明 + 重试"已覆盖在上表"读取失败"与"加载"两行，优先级同步上调。

## 四、优先级矩阵

按「用户可感知收益 / 改动成本 / 风险」排序的建议顺序：

| 顺序 | 事项 | 收益 | 成本 | 风险 |
|---|---|---|---|---|
| 1 | 修 E1（退出后接入请求无人承接）—— **但要作为独立专题，先在目标设备上复现再定形态** | 高（电视端是常驻用法）/ 低（很少用） | 中高 | 中高 |
| 2 | 第 1 批修"真错"（10 条） | 中高 | 低 | 低 |
| 3 | 第 0 批截图基线 | 中（是后续所有工作的前提） | 低 | 无 |
| 4 | 控制台信息层级重排（R2） | **最高** | 中 | 低 |
| 5 | `ScreenScaffold` + 二级页返回（R1） | 高 | 中 | 低 |
| 6 | 电视端焦点系统（`focusRequester` + 统一容器 + `BackHandler`） | 高 | 中 | 中 |
| 7 | design token 化 + CSS 单层化（R3） | 中高 | 中 | 低 |
| 8 | 深色模式补齐（含 `themes.xml` 联动） | 中高 | 中 | 低 |
| 9 | 网页端搜索 / 大目录性能 | 高 | 高 | 中 |
| 10 | 抽公共组件 + 文案统一 | 中 | 中 | 低 |

**如果只有一周**：做 **2、3、4、5**（第 1 批十个"真错" → 截图基线 → 控制台重排 → `ScreenScaffold`）。

> **这里修正了初版的一处内部矛盾**：初版把 E1 列在优先级第 1，却又把"修 E1"塞进一周批次 —— 而 E1 是清单里成本最高的项，这两件事互相冲突。评审指出"一周内同时完成多端截图基线、Android UI 改造、电视焦点、通知承接、网页搜索与性能，容易把多个高风险改动挤在一起"，**这个判断是对的**。E1 应单独立项，先复现再选形态。
>
> 另：`ScreenScaffold` 与"控制台重排"会改同一批文件，建议**合为一批做完再回归**，不要拆成两次编译。

**关于 token / 深色模式的排序，两方意见合起来才是对的**：
评审主张"深色模式和设计 token 属于全局整理，放在具体行为缺陷之后更稳妥"，同时又说"应分开实施和验收，不必先做大规模 CSS 重写"。
折中做法是**把它切开**：
- **随第 1 批做**（修缺陷必需的部分）：`tertiary` 定义、3 处硬编码色、`themes.xml` 与 `MainActivity` 的系统深色联动、`Banner` 的 Warn/Success 自适应。这些不改会一直往外冒新缺陷。
- **延后做**（纯整理）：Compose 间距/圆角 token 全量收敛、网页端 CSS 合并单层 + `:root` 变量。这些是"减少重复劳动"，不修也不影响正确性。
- 这样既不把全局重写卡在关键路径上，也避免同一个屏被改两遍。
