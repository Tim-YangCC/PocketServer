| 需求点 | 实现位置 | 关键说明 |

### FR-7 传输任务与日志

| 需求点 | 实现位置 | 关键说明 |
|---|---|---|
| 任务列表 | `ui/phone/TransfersScreen.kt`<br>`data/repo/Repositories.kt`（`TransferRepository`） | 进行中任务同时给百分比、字节数、**并行路数** |
| 残留任务清理 | `TransferRepository.failStaleTasks` | 进程被杀后把"进行中"标记为失败，避免永远转圈 |
| 访问日志 | `ui/phone/LogsScreen.kt`<br>`LogRepository` | 用 `Channel` 批量提交（300ms / 32 条），避免逐条事务拖慢首屏 |
| 日志可读性 | `LogsViewModel.actionLabel` | 把 HTTP 方法与路径翻译成「下载文件」「浏览目录」 |
| 异常高亮 | `AccessLogEntity.looksAbnormal` | 只有 4xx/5xx 才标红，且排除 favicon 探测 |
| 日志上限 | `AppConstants.ACCESS_LOG_MAX_ROWS` | 超出后按时间淘汰 |
| 统一记账入口 | `data/repo/TransferRecorder.kt` | 非挂起句柄 + 每传输一条 `Channel`，单协程串行落库，保证 `insert → update → finish` 顺序；进度只前进 |
| 网页上传记账 | `HttpFileServer.handleUpload`<br>`handleReserve` | 分块 PUT 按目标路径归并成**一条**记录（`PendingUploads`）；完成判定数分片而不是看磁盘大小 |
| 网页下载记账 | `HttpFileServer.handleDownload` | 只给 `/dl` 记账；`/view` 预览不记（视频预览会连发几十个 Range 请求） |
| WebDAV 记账 | `WebDavHandler.get` / `put` | 映射成网络驱动器后的收发同样留记录；`HEAD` 不算传输 |
| FTP 记账 | `FtpServer.doRetr` / `doStor` | 兼容通道也要留记录；FTP 协议不告知上传大小，故只显示已收字节数 |
| 设备互传记账 | `ServerController.pushTo` / `pullFrom` | 原有路径，方向为 PUSH / PULL |
| 传输控制权威 | `data/repo/TransferControl.kt` | 控制意图（运行中 / 已暂停 / 已取消）**只存在服务端一处**。网页上传的执行者是用户浏览器、手机互传的执行者是协程，两端都只是客户端，各自轮询同一份意图 |
| 网页端控制入口 | `HttpFileServer` 的 `/api/fs/control` | 按**路径**下达。`TransferRecorder.begin()` 返回句柄时记录还没落库，HTTP 循环在任何一个时刻只知道路径，id 只能当副索引 |
| 在飞分片的停手信号 | `HttpFileServer.handlePut` → **423 / 410** | 423 = 已暂停、410 = 已取消。有了这两个码，浏览器才能把"用户让我停"和"网络坏了"分开，不会傻乎乎地重试 |
| 状态对账通道 | `HttpFileServer` 的 `GET /api/fs/tasks` | 网页每 2 秒拉一次。局域网这个粒度够用，因此没有为它引入 WebSocket 长连接 |
| 手机端传输出口 | `ui/phone/TransfersScreen.kt`（概览条 + 行内按钮） | 概览：进行中 / 已暂停 / 已完成 / 未完成；「开始」只对已暂停的行出现 |
| 网页端传输出口 | `WebUi.filePage`（`#oview` + `actionsFor`） | 概览四格计数 + 剩余字节；行内按钮按状态给（进行中→暂停/取消，已暂停→开始/取消）；**终态行不再画按钮**；下载只给取消 |
| 取消的墓碑期 | `AppConstants.CANCEL_TOMBSTONE_MS`（60s） | 取消后在途的迟到分片被挡回，免得那半截文件被当成一次全新上传又传一遍 |
| 暂停不退出消费协程 | `TransferRecorder.consume` | 收到收尾信号而闸门正卡在暂停上时必须 `continue`；一旦走到 `unregister`，按「开始」就再也接不上了 —— 暂停会变成死路 |

### FR-13 后台保活（息屏 / 切后台仍可传输与被传输）

| 需求点 | 实现位置 | 关键说明 |
|---|---|---|
| 传输期 CPU 唤醒锁 | `core/KeepAlive.kt`（`acquireTransferWakeLock`） | 原实现**只给电视端**加了 CPU 锁，手机端在传输期间完全没有 —— 与"手机也要能后台传"直接矛盾。Wi-Fi 锁还在但没人从 socket 读，一样是断 |
| Wi-Fi 高性能锁 | `core/KeepAlive.kt`（`onServerStarted`） | 整个服务生命周期常驻持有，而不是"传输时才抢"。收到连接再抢锁的那段窗口正好是固件已进省电档的时刻，表现为"第一次连接特别慢" |
| 锁的引用计数 | `KeepAlive.activeTransfers` | 归零后延迟 `TRANSFER_LOCK_LINGER_MS` 才放锁：传文件夹会连发几十个 PUT，一归零就放锁会让射频反复进出省电态 |
| 计数不归零的兜底 | `KeepAlive.acquireTransferWakeLock` | 用 `acquire(timeout)` 而不是裸 `acquire()`。收尾路径有正常完成 / 连接断开 / 写盘失败 / 进程被杀四类，漏一条就会永久持锁耗电 |
| 五通道统一接入 | `data/repo/TransferRecorder.begin` | 网页上传/下载、WebDAV、FTP 四条通道**完全不经过** `ServerController`，只有 `begin()` 是共同点 |
| 设备互传接入 | `ServerController.pushTo` / `pullFrom` | 这两条不走 `TransferRecorder`（直接写仓库），单独接线 |
| 在跑条数从表派生 | `ServerController.liveTransferCount` | 自己维护计数器只能数到设备互传那一类 |
| 卡死兜底 | `AppConstants.TRANSFER_IDLE_TIMEOUT_MS`<br>`TransferRecorder.nextOp` / `closeStaleTransfer` | 十分钟没有任何进度即判中断。这不只是修 bug：落库协程挂死会让保活计数永不归零，把「空闲自停」静默关掉 |
| 电池优化白名单 | `KeepAlive.isIgnoringBatteryOptimizations`<br>`batteryOptimizationIntent` | Doze（息屏 + 静止 + 未充电）会**直接掐断网络**，前台服务只能延缓不能豁免。这三条正好是"手机放桌上当服务器"的场景 |
| 国产 ROM 引导 | `KeepAlive.oemBackgroundHint` | 小米 / 华为 / OPPO / vivo 等在官方白名单之外**再拦一层**，用户按官方做法加完白名单仍会被杀 |
| 传输进度通知 | `ServerForegroundService.buildTransferNotification` | 独立通知（ID 1025）。总进度按 **5% 分档**，一个任务全程最多 20 次更新；速度刻意不进通知文案 |
| 保活自检 | `ServerController.keepAliveDiagnostics` | 三个锁到底有没有真的拿到，供用户自查"我明明开了后台还是断" |

> 这三件事必须**同时成立**才有效：前台服务让进程不被回收、Wi-Fi 锁让射频不进省电档、
> CPU 锁让数据到了网卡真的有人读。少任何一件，用户看到的现象都是同一句"一到后台就断"。

### FR-14 断点续传

| 需求点 | 实现位置 | 关键说明 |
|---|---|---|
| 进度模型 | `data/repo/UploadResumeStore.kt`（`UploadSession`） | 权威是**每路已写结束位点**，不是已收字节总数：某一路失败重传会重写同一段，累加会被算两次（进度冲过 100%、误判完成） |
| 一个模型覆盖三种情况 | `UploadSession.expectedEnd` / `laneDone` / `isComplete` | 单路就是 `lanes = 1`；单路续传、多路并发、失败重传共用同一套判定 |
| 与服务端的切段契约 | `UploadSession.expectedEnd` ↔ `WebUi.kt` 的 `Math.floor(size / lanes)` | 两边不一致 → 某一路永远等不到完成，记录永远停在"进行中"，且不报任何错 |
| 会话持久化 | `UploadResumeStore`（TSV + Mutex + tmp/rename） | **先写 tmp 再 rename**：直接覆写被杀会得到截断的表，坏行被跳过后表现为"部分会话静默消失" |
| 会话查询接口 | `HttpFileServer.handleUploadStatus`（`GET /api/fs/upload-status`） | 单路大文件没有"分片"概念，只能靠它问服务端"你那边现在有多少字节" |
| 续传命中判定 | `HttpFileServer.handleReserve` | 必须放在 dedupe **之前**：上次中断的半截文件已占原名，走 dedupe 会被改名成「xxx (1).bin」，续传永远命中不了自己 |
| 会话对不上时只丢会话 | `HttpFileServer.handleReserve` | 只 `remove` 会话、**不删文件**。万一那是"传完了会话没来得及删"，删掉就毁了用户一个完好文件 —— 毁文件与占空间之间选占空间 |
| 位点推进与完成判定 | `HttpFileServer.advanceSession` / `handleUpload` | 有会话时完成以会话为准（幂等），没会话的第三方脚本才退化为"一个请求 = 一个完整文件" |
| 网页端续传 | `WebUi.kt`（`queryResume` / `putSlice` / `runLane`） | 续传起点**必须问服务端**：`xhr.upload.onprogress` 报的是"交给了 socket 缓冲"，拿它当起点会跳过一段没落盘的字节 —— 文件大小正常但打开是坏的 |
| 首传不能带 offset | `WebUi.putSlice` | `offset=0` 与"不带 offset"**不是一回事**：带上就走随机写通道，SAF 不支持随机写会直接 409 |
| 断线重试 | `WebUi.runLane`（`MAX_LANE_RETRY = 3`） | 每路失败后回头问一次服务端位点再接着发，最多 3 次；SAF 通道则明确告知"该通道不支持续传，正在从头重传" |
| 会话过期回收 | `AppConstants.UPLOAD_RESUME_TTL_MS` + `CacheJanitor.cleanAbandonedUploads` | 24 小时未继续即随会话一起删。只清表不删文件的话，磁盘上会留下一个"大小看起来完全正常"的残片 |

### FR-15 存储与清理

| 需求点 | 实现位置 | 关键说明 |
|---|---|---|
| 先列清垃圾来源 | `data/repo/CacheJanitor.kt`（`scan`） | 四类：测速临时文件、上传残片、两张只增不减的表、应用缓存目录 |
| 半截文件在磁盘上认不出来 | `CacheJanitor.scanSessionFiles` | 分块上传按最终大小预分配（O-11），传到 10% 就断的话磁盘大小已等于整文件 —— 用户和系统都识别不出它是残片，**唯一能认出它的是会话表** |

| 分类明细而非黑箱结论 | `CacheJanitor.Report` / `Item` | 每项写清「是什么、多少字节、多少条、为什么可以删」。只报"已清理 12.3MB"只会让人怀疑到底清了什么 |

| 接上从未被调用的 `pruneOld()` | `ServerController.runAutoClean` | 该方法写好了却一直没有调用方 —— 传输记录此前**没有任何淘汰机制** |

| 保活引导 | `ui/phone/BackgroundAndCleanup.kt`（`KeepAliveSettingsSection`） | 挂在设置页「省电与常驻」之后；按 Activity `ON_RESUME` 重取系统状态（系统设置变了没有任何回调能到应用里） |

## 四、实现过程中发现并修正的缺陷

| 缺陷 | 后果 | 修正位置 |
|---|---|---|
| `verify()` 中"配对码已过期"分支永远不可达 | 用户拿着旧码输入会看到"配对码不正确，还能试 4 次"，从而反复试到被锁定；真实原因（码已换）完全没提示 | `PairingManager.verify` — 过期判断移到 `ensureCode()` **之前** |
| 策略类设置不随 DataStore 更新 | 设置页把「允许删除」关掉，界面显示已关闭，但服务端仍会放行删除 —— "界面说关了、后台还开着" | `ServerController` 增加 settings collector |
| 设置页 Flow 用法错误（`map(flow)`） | 编译失败 | `FilesAndSettingsViewModel` 改为标准 `map { }` |
| 电视端配对码字号 18sp | 达不到 FR-10.4 的"3 米外可读"（55 吋屏幕 3 米视距需 ≥48sp） | `PairingCodeText` — TV 56sp / 手机 32sp |
| 手机端配对码字号 10sp | 比正文（14sp）还小，用户要照着敲进电脑，极易读错重试 | 同上 |
| 分享进来的文件未先落地 | 对端拿不到我们的 `content://` URI | `util/ShareImporter.kt` + `MainActivity.consumeIntent` |
| 分支上传未先占位 | 四条连接各自改名，生成四块互不相关的残片 | `HttpFileServer.handleReserve` + `WebUi` JS 改为先 reserve |
| `SocketReader` 预读导致无法零拷贝 | 框架预读几 KB，`transferFrom` 用不上 | `HttpCore.kt` 自管行缓冲 + `drain()` |
| `PathUtil.sanitize` 先 `trim()` 再查控制字符 | 控制字符被 trim 静默吃掉：请求 `a/\tb/c` 被"修好"成 `a/b/c`，即畸形路径打开了另一个真实文件（典型别名漏洞） | `util/PathUtil.kt` — 控制字符判定移到任何归一化动作**之前**，并取消逐段 `trim()` |
| `SharingPolicy.canMkdirAllowed` 缺少对 `allowRename` 的单向依赖 | 关掉"重命名"后仍能新建文件夹，留下"能建不能改"的半开口子 | `net/SharingPolicy.kt` — `canMkdirAllowed` 增加 `allowRename` 条件 |
| `QrCodec` 设备名无长度上限 | 最坏情况（长中文名 + 长 IP）载荷 174 字符，超出 160 预算 → 模块数上升、3 米外扫不动（违反 FR-10.4 的设计前提） | `net/QrCodec.kt` — 设备名截断至 10 字符并加省略号 |

### 4.1 真编译与真跑测试暴露的问题

下面这些问题**只有真正编译、真正跑测试才会暴露**，纯代码 review 看不出来。经本机构建验证（详见第五节）：

| 问题 | 后果 | 修正位置 |
|---|---|---|
| `WriteSink.channelOrNull` / `streamOrNull` 被当作函数调用（4 处） | 编译失败。根因是两个接口形状不一致：`ReadSource` 用**函数**，`WriteSink` 用**属性** | `FtpServer`、`WebDavHandler`、`PeerClient`、`ShareImporter` 统一按属性访问 |
| `SafStorageProvider.openWrite` 把 `Uri?` 接在 `String?` 上 | 编译失败（Kotlin 将其对齐为 `Comparable<...>?`）。即便能编译，后续 `buildDocumentUriUsingTree` 需要的是 docId 字符串，不是 Uri | 抽出 `createDocumentId()`，显式 `getDocumentId()` 转一次 |
| `wm?.createWifiLock(...).apply { acquire() }` | 编译失败。更危险的是"顺手改成 `?.apply`"会让 `acquire()` 静默不执行 —— 息屏掉速的毛病会原样回来 | `ServerController.acquireLocks` 改为先判空再调用 |
| `BottleneckDiagnoser` 形参名 `zeroCopySender` 与实参 `zeroCopy` 不匹配 | 编译失败 | `ServerController.runSpeedTest` 用具名实参显式对齐 |
| `HttpExchange.respondDetail` 的 setter 是 `private` | 编译失败 —— 写它的 `HttpFileServer`/`WebDavHandler` 是同模块的兄弟类，不是内部类 | `HttpCore.kt` 改为 `internal set` |
| `PeerClient` 导入 `ChunkedTransferEngine.TransferOutcome` | 编译失败：`TransferOutcome` 是 `perf` 包下的顶层类，不是嵌套类 | 改为 `import com.pocketserver.perf.TransferOutcome` |
| `jvmToolchain(17)` 要求机器上存在**确切** 17 版 JDK | 在只装了 Android Studio 自带 JDK 21 的机器上**直接构建失败**（`NoToolchainAvailableException`） | `app/build.gradle.kts` 改为「JDK 17+ 编译、产出 JVM 17 字节码」，不再锁死工具链版本 |
| `android.defaults.buildfeatures.buildconfig` 已在 AGP 9 移除 | 每次构建都报警告，且 AGP 9 会直接失败 | 从 `gradle.properties` 移除（`buildFeatures.buildConfig` 已显式开启） |
| 死代码：`BottleneckDiagnoser.unusedMax()`、`QrScanActivity.unusedNotFoundException()` | 前者连 `max` 的 import 都没有，属于编译不过的残留；后者是纯噪声 | 两处均删除 |
| Compose 弃用：`Icons.Filled.InsertDriveFile` / `Article` | 告警；RTL 语言下图标会被错误镜像 | 改用 `Icons.AutoMirrored.Filled.*` |
| 用例 `错误计数超出统计窗口后清零` 与修正后的 `Expired` 行为冲突 | 用例把时间推进到越过配对码有效期，却仍用旧码断言 `Wrong(4)` | **不是放宽断言**：改为按现实语义取一次"当前屏幕上的码"，与新行为互补 |
| 已完成 / 失败 / 已取消的行上仍然挂着「暂停 / 取消」按钮 | 2 秒一次的轮询把按钮重新画了上去，用户点下去得到的是一个早就结束的任务；断言层面全过，只有真去点一下才发现（E2E 抓出） | `WebUi.filePage` — 行句柄加 `finish()` / `isTerminal()`，三种终态统一清空按钮，`applyTasks` 只对**非终态**的行重画 |
| 控制指令改的是"记录状态"，而 PUT 逻辑查的是"闸门状态" | 暂停 / 取消在界面上看着生效了，实际那几路还在传（假后端与真服务端同时踩到） | 控制端点统一改闸门（`TransferControl`），`/api/fs/tasks` 的状态也取闸门 |

### 5.3 本机排障：`testDebugUnitTest` 起不来

本机执行 `gradle :app:testDebugUnitTest` 会失败，报：

```
错误: 找不到或无法加载主类 worker.org.gradle.process.internal.worker.GradleWorkerMain
```

**这不是工程问题**，而是本机环境问题：Gradle 为 fork 出的测试 JVM 传递 classpath 时，
非 ASCII 路径（用户名 `登录`）被有损转码。把 Gradle 发行版与 `GRADLE_USER_HOME` 都换到
`C:\psbuild` 这样的纯 ASCII 路径后依然复现，说明问题在 JVM 侧而不在路径本身。

绕开办法（已验证）：测试代码本身能正常编译，直接用 `java` 跑 JUnit 即可 ——
用 init script 把 `testDebugUnitTest` 的 runtime classpath 导出，再 `JUnitCore` 执行：

```powershell
# 1) 导出 classpath（-I 传入，不修改工程）
gradle -I dump-cp.init.gradle :app:dumpTestClasspath
# 2) 直接跑（注意 PowerShell 5.1 必须显式 -Encoding UTF8，否则中文路径会被按 GBK 读错）
$cp = (Get-Content -Encoding UTF8 'C:\psbuild\test-cp.txt') -join ';'
java -cp $cp org.junit.runner.JUnitCore com.pocketserver.net.PairingManagerTest ...
```

> 在用户名不含中文的机器上，`gradle testDebugUnitTest` 应当可以直接使用。
> 交付验收时优先用标准命令，本节的绕过方式仅作为受限环境的备选。

## 六、本轮修复：电脑端网页（用户反馈驱动）

反馈原话：

> pc 访问地址后只能上传文件呀。而且我发现我拖进去的 html 文件被浏览器直接打开了，
> 并不能传给手机。且我需要可以上传文件夹的功能你也没有。同时我在浏览器里也不能看到手机存储里的内容。

### 6.1 四条问题与根因

| 现象 | 根因 | 修正 |
|---|---|---|
| 拖 html 进页面被浏览器直接打开 | `dragover`/`drop` 只挂在列表区域的 `#drop` 上。拖到页头、面包屑、任务区或页面空白处时没有任何监听器拦默认动作，浏览器就把本地文件当成导航目标 | `WebUi.filePage` — 改为 window 级监听 + 无条件 `preventDefault`，配 dragenter/dragleave 计数控制的遮罩 |
| 不能上传文件夹 | 只有一个 `<input type="file" multiple>`，没有 `webkitdirectory`；拖入目录时 `dataTransfer.files` 只有文件、没有结构 | 新增「上传文件夹」按钮与 `webkitdirectory` 输入框；拖拽走 `webkitGetAsEntry()` 递归遍历，保留层级与空目录 |
| 浏览器里看不到手机存储内容 | ① 网页端把所有失败都吞掉了 —— `load()` 只处理 401，其余 `ok:false` 一律按空数组渲染；② 存储根落到了**应用私有目录**（未授予「所有文件访问权限」时的兜底），那里本来就没有用户文件；③ 授权后也不会自动重取 —— `StorageAccessManager.build()` 只在 `start()` 求值一次 | ① `load()` 改为原样展示 `d.error` 并弹提示，新增共享位置横幅；② 新增 `StorageShare`，把「共享的是哪块空间」随每个列表响应下发；③ 新增 `refreshStorageIfChanged()`，Activity 回前台时比对根指纹并重建协议栈 |
| 只能上传文件 | 页面只有一条虚线拖拽提示，没有任何工具栏 | 新增工具栏：上传文件 / 上传文件夹 / 新建文件夹 / 重命名 / 删除 / 下载 |

> 「看不到文件」这条是本轮最值得记的一条：**产品没有说出真相**。

## 七、本轮修复：传输记录只覆盖了设备互传（用户反馈驱动）

用户在真机上发现：「电脑给手机传内容，在『传输任务』页没有留下记录」。

### 7.1 根因：主通道根本没接线

`TransferTaskEntity` 只有两个写入方 —— `ServerController.pushTo` / `pullFrom`，
也就是「附近」页的设备互传。而**本产品的主通道是电脑浏览器**
（`HttpFileServer`），用户最常做的动作就是拖文件进网页，这条路径一个字节的记录都不留。
WebDAV 与 FTP 同样没有。

一个能佐证"这是遗漏而非设计"的细节：`TransferDirection` 里 `UPLOAD` / `DOWNLOAD`
两个枚举值、以及 `TransfersViewModel.directionLabel` 里「电脑上传 / 电脑下载」
两条文案早就写好了，只是从来没有人往里写数据。同样地，
`TransfersScreen` 空状态那句话——「在电脑网页上传下载，或者在「附近」页给另一台设备
发文件，这里都会留下记录」——在修复前是**不成立的**：界面承诺了一件代码没做的事。

### 7.2 修复要点

| 问题 | 处理 |
|---|---|
| 记账动作必须在同步阻塞的协议循环里发起 | 新增 `TransferRecorder`：`begin()` 立刻返回一个**非挂起**句柄，内部把动作丢进每条传输一个的 `Channel`，由一条协程串行落库 |
| 多来源上报导致进度乱序 | 消费协程维护"水位"，`transferred` 只增不减，界面进度条不会回退 |
| 分块上传会让一个文件变成 2~6 条记录 | `handleReserve` 登记目标路径（每个文件一次），同路径的 PUT 归并到同一条记录上 |
| **完成判定不能用磁盘大小** | 分块写入会先 `setLength(offset + 本块长度)` 预分配，文件大小在第一个分片到达时就等于整个文件了。改为数分片：`reserve` 带上 `lanes`，等齐了才收尾 |
| 只 reserve 不上传（用户取消）会留下僵尸记录 | 记录在**第一次真正写字节**时才建；登记项有 30 分钟 TTL，超时判为「上传未完成」 |
| 视频预览会刷屏 | 只给 `/dl` 记账，`/view` 不计 |
| 记账失败连累传输 | 所有落库都包 `runCatching`；拿不到 id 时静默跳过，文件该传还是传完 |

`reserve` 的 `size` / `lanes` 由网页端提供，客户端与服务端必须用**同一套**
分片算法（`laneCount`）—— 两处不一致的后果是服务端一直等一个等不到的分片数，
记录永远停在"进行中"，且不会有任何报错。这条已写成 E2E 断言。

## 八、本轮修复：传输列表只能看，不能管（用户反馈驱动）

反馈原话：

> 我发现传输的时候 网页端缺少传输任务概览 ，暂停 ，开始，取消按钮。手机端传输列表
> 也缺少暂停 开始 取消按钮。请你补齐

### 8.1 根因：两端都只有"显示器"，没有"方向盘"

手机端的「传输任务」页本来就能看到每一条传输的百分比与字节数，网页端顶部也有一条在走的进度条。
但**两端都没有任何一处向服务端表达过"停下来"这个意思** —— 缺的不是按钮，是**指令通道**：

| 端 | 修复前 | 缺的东西 |
|---|---|---|
| 手机端 | 列表 + 进度 + 方向标签 | 概览、以及每行的暂停 / 开始 / 取消 |
| 网页端 | 一条横幅进度条（只反映"当前这一个文件"） | 连"现在一共在传什么"都看不到，更没有控制 |

一个能佐证"这是遗漏而非设计"的细节：`TransferTaskEntity` 里 `status` 字段早就能存
运行中 / 已完成 / 失败之外的状态，界面文案里也一直写着「进行中」——
只是从来没有人往里写过"已暂停"，也没有人能从界面下达这个状态。

### 8.2 关键决策：控制意图只能有一个权威

这是本轮唯一需要想清楚的地方，也是实现里最容易做错的地方。

网页上传的**执行者是用户自己的浏览器**——服务端够不着它，没法"替它停下"，
只能等它下一次来请求时告诉它"你已经暂停了"。手机互传的执行者是手机里的协程，
倒是服务端自己家的事。**如果让两端各自记一份状态，就一定会出现
"手机说暂停了、电脑还在传"，用户无法判断该信谁。**

所以：**控制意图（运行中 / 已暂停 / 已取消）只存在服务端的 `TransferControl` 一处，
两端都退化成客户端**，各自读同一份意图。

```
手机端按钮 ─┐
            ├─→ TransferControl（服务端唯一权威）
网页按钮   ─┘         │
                      ├─→ 在飞分片收到 423/410，立刻停手
                      └─→ 两端各自轮询/观察，把行状态对齐
```

| 环节 | 做法 |
|---|---|
| 下达 | `POST /api/fs/control`，带**路径**与动作 |
| 对账 | 网页每 2 秒 `GET /api/fs/tasks`；手机端直接观察同一份意图流 |
| 停手 | 正在飞的分片收到 **423（已暂停）/ 410（已取消）** |
| 续传 | 「开始」后从各自断点接着发，已经传完的那几路不重传 |

选择轮询而不是推送：局域网里 2 秒的粒度已经够用，而 WebSocket 要多一套长连接、
心跳与断线重连。**换来的只是"早 2 秒看到"，不值。**

### 8.3 三个必须守住的细节（改动时别退回去）

1. **路径才是主键，记录 id 只是副索引。**
   `TransferRecorder.begin()` 返回句柄时，记录还没落库、id 还不存在，
   HTTP 循环在任何一个时刻手里只有路径。所以控制指令一律按路径下达。
   （`TransferControlTest` 里按 id 下达的两个用例，正是为了锁住"暂停需要搬运工、
   取消不需要"这个不对称。）

2. **暂停不能退出消费协程。**
   收尾信号到了、而闸门正卡在暂停上时必须 `continue`。一旦顺着这条路径走到
   `unregister`，按「开始」就再也接不上了 —— 暂停变成一条死路，
   而且**不报任何错**，用户只会觉得"这个按钮坏了"。

3. **最终状态由用户意图决定，不由这一路是成功还是失败决定。**
   否则会出现"用户点了取消，界面先跳到已取消、一秒后又跳回失败"——
   而这只是因为在途的那个分片刚好在这时候返回了 500。
   同理，取消后在途的迟到分片会被 **60 秒墓碑期**挡回去，
   免得那半截文件被当成一次全新上传又传一遍。

### 8.4 网页端：为什么下载只给「取消」，不给「暂停」

浏览器的能力边界，不是偷懒：**下载一旦开始，浏览器没有
"挂起这个下载、稍后从断点接着下"的接口**。按了暂停也只能断开重来，
那和取消是同一件事，给用户两个结果一样的按钮只会让人困惑。
暂停 / 续传只对**上传**成立 —— 因为上传的每一路已写位点都记在手机端。

只读会话下，上传行不给任何控制按钮（本来就不该有上传），下载行仍然可以取消。

网页是 `WebUi.kt` 里的一段 Kotlin 原始字符串，**编译器不会看里面的任何字符**。
本轮为它建了两套脚本，都坚持**从 Kotlin 源现场渲染**再跑：

| 脚本 | 方式 | 覆盖 | 结果 |

> 测试会**全部通过**——它测的是上一版页面，而且不会有任何提示。

根因是 2 秒一次的轮询会把按钮重新画上去 —— 假后端返回的那一行是终态，

`done` / `fail` / `canceled` 统一清空按钮，`applyTasks` 只对**非终态**的行重画。
